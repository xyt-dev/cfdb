**Problem A**

To get the maximal possible result you have just to sort summands in non-decreasing order by coefficients (counting coefficients with preceeding signs + and -). You should not pay attention to 'a++' or '++a'! The question is: why is it true?

First, consider an expression with only 'a++'. Then our assertion is obvious: it is better to multiply 'a' by small coefficients when it has small value, and by large coefficients, when it becomes larger. The same also takes place in case of negative coefficients or a-value. Of course, it is not a rigorous proof. I hope you will think on it if you haven't get it yet.

Second, consider the expression *k* * *a* +  +  + *k* *  +  + *a*, where *k* is some coefficient equal for both summands. Let initial value of 'a' equals to *a*<sub>0</sub>. Calculating the value of the expression both ways, we obtain: *k* * *a*<sub>0</sub> + *k* * (*a*<sub>0</sub> + 2) = *k* * (*a*<sub>0</sub> + 1) + *k* * (*a*<sub>0</sub> + 1). So in this case the order is immaterial.

Third, let us have the expression *k* * *a* +  +  + *l* *  +  + *a*, where *k* and *l* are two distinct coefficients. This expression can have two different values: *k* * *a*<sub>0</sub> + *l* * (*a*<sub>0</sub> + 2) and *k* * (*a*<sub>0</sub> + 1) + *l* * (*a*<sub>0</sub> + 1). The first value is greater than the second one if and only if *k* < *l*. We can deal with the expression k*++a+l*a++ analogously.

Thus if we have two succesive summands with the same coefficient, we may swap or not to swap them. If we have two succesive summands with distinct coefficients, we must put the summand with a smaller coeficient first. Applying these considerations while it is necessary, we get a sequence of summands sorted by coefficients.

Let us reformulate the problem. Given a set of segments on a line, and the task is to find the largest subset such that segments in it don't intersect ``partially''. Two segments [*a*, *b*] and [*c*, *d*] intersect partially, if, for instance, *a* < *c* < *b* < *d*.

Take all the ends of the given segments, sort them, and compute the dynamics: *d*<sub>*l*, *r*</sub> is the largest possible size of such subset that segments in don't intersect partially and located between the *l*-th end and the *r* end (in sorted order), inclusively. We want to compute *d*<sub>*l*, *r*</sub> having already computed *d*<sub>*i*, *j*</sub> for all *l* ≤ *i* ≤ *j* ≤ *r*, but [*i*, *j*] ≠ [*l*, *r*]. First put *d*<sub>*l*, *r*</sub> = *d*<sub>*l* + 1, *r*</sub> if we don't take segments with the left end in *l*. Now process the segments with the left end in *l*. If the segment [*l*, *r*] exists, we undoubtedly take it to our set. If we take another segment, say, [*l*, *i*], where *i* < *r*, look at segments [*l*, *i*] and [*i*, *r*] (we have  answers for them already computed) and try to update *d*<sub>*l*, *r*</sub>. The asymptotics is *O*(*n*<sup>2</sup>), because  the total number of left ends is *O*(*n*). Then you have to output the certificate, i.e. the optimal set itself. It can be done in the standard way.

**Problem E**

The number of ways to put *b* items into *a* boxes is, of course, *a*<sup>*b*</sup>. So we have an acyclic game for two players with positions (*a*, *b*) for which *a*<sup>*b*</sup> < *n*. Unfortunatly, there exists an infinite number of such positions: *a* = 1, *b* is any. But in this case, if 2<sup>*b*</sup> ≥ *n*, it is a draw position, because the only way for both players (not leading to lose) is to increase *b* infinitely.

Another special case is a position with *b* = 1 and rather large *a*. Namely, if

Problem K

Problem K has a great number of different solutions, so I'm surprised that there was a lack of them during the contest. Solutions with time *O*(*k*<sup>4</sup>) and even some *O*(*k*<sup>5</sup>) solutions with optimization were acceptable, but [KADR](<https://codeforces.com/profile/KADR>) describes even better solution in *O*(*k*<sup>3</sup>) ([http://codeforces.com/blog/entry/793](<https://codeforces.com/blog/entry/793>)).

Here are some jury ideas of this problem. First, let us compress the coordinates. Choose a labeled point in each object and compute by the standard dynamics the number of such labels in each rectangle. It takes *O*(*k*<sup>4</sup>) to process all possible rectangles. The problem arises that a rectangle may contain a valid number of objects, but contain some objects not completely. To prevent this, we can check the borders. They are segments parallel to the coordinate axes, and their number is *O*(*k*<sup>3</sup>). So we can precalc for them if they are valid or not comparing them with each object. Then we have to come back to uncompressed coordinates.

The following solution is *O*(*k*<sup>5</sup>), and it uses the limitation on the number of objects (3) inside the rectangle. Process all the triples of objects (the same, of course, with pairs and single objects). Fix a triple, and change it by a single big object. Then move from the resulting object up (and then down), and check if a row above (or below) can be included in a striked rectangle. For each row we find a longest segment [l, r], which contains the current big object and doesn't contain others. Using this information, one can easily calculate the total number of rectangles that contain the current triple.
